Yang pindah aturan alurnya, bukan agennya

Di workflow sumber Foundry, ada aturan untuk memilih dan memanggil agent. Kita pindahkan aturan itu (orkestrasi), sedangkan agent, model, koneksi tool, izin, dan data tetap harus disiapkan terpisah. Tiga jalur ini pilihan alternatif, bukan tiga langkah yang dilakukan berurutan.

Pilih berdasarkan cara tim mengelola alur

A · Kode Python

MAF code-first

Compiler membaca YAML sumber dan membuat mapping. Python membangun graph lewat WorkflowBuilder. Cocok kalau tim perlu kontrol dan pengujian detail di kode.

Buka workshop MAF code-first

B · Workflow YAML

MAF declarative

Python menyiapkan agent, lalu WorkflowFactory membaca aturan langsung dari YAML. Cocok kalau alur perlu tetap terbaca sebagai file; cek kompatibilitas action dan SDK.

Buka workshop MAF workflow YAML

C · Workflow native Azure

Azure Logic Apps

Definisi dipetakan ke Workflow Definition Language (WDL). Azure menjalankan Request, Switch, dan Response. Cocok kalau tim perlu membaca node dan Run history di portal.

Bandingkan setup, perubahan alur, dan biaya ketiga jalur.

Ikuti satu pertanyaan sampai jawabannya kembali

Pakai input yang sama untuk menguji tiap jalur

{"question":"Show work orders for equipment TRK001."}
Route / status
mcp / success
Fakta
WO001 untuk TRK001
Sumber
urn:kppdemo:maintenance/TRK001

Bandingkan fakta, sumber, dan status, bukan susunan kalimat. HTTP 200 atau action berstatus Succeeded saja belum membuktikan data ditemukan. Uji live butuh sandbox yang sudah siap dan bisa menimbulkan biaya.

Siapkan lingkungan, lalu coba satu jalur

  • Checklist setup bersama dan contoh hitung biaya.
  • Profil runtime untuk sandbox sendiri dan katalog input uji.
  • YAML sumber Foundry dan rekaman demo sebelumnya.

Untuk belajar offline, unduh ZIP atau clone repository, lalu buka docs/index.html dari folder hasil ekstrak. Halaman, diagram, interaksi, dan screenshot tidak bergantung internet; tautan ke GitHub dan Microsoft Learn membutuhkannya.
